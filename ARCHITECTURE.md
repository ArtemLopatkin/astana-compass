# Архитектура Astana Compass

Репозиторий: https://github.com/chinusoid/astana-compass

Astana Compass — городской помощник, который находит реальные места в Астане, объясняет выбор и строит выполнимый план с учётом времени, местоположения и ограничений пользователя. Архитектура рассчитана на независимую работу нескольких AI-агентов и последующее объединение через pull request.

## 1. Основные решения

- Frontend: Next.js, TypeScript, Tailwind CSS, MapLibre GL JS. Интерфейс работает на русском, казахском и английском.
- Backend: FastAPI, Pydantic, SQLAlchemy, Alembic; Python-пакеты запускаются через uv.
- Хранилище: PostgreSQL с pgvector. Структурированные данные, provenance, текстовый поиск и embeddings находятся в одной БД.
- Локальный запуск и deployment: Docker Compose. Frontend и API — отдельные процессы; база — отдельный сервис.
- JavaScript-зависимости: pnpm. Версии runtime и библиотек, manifests и lockfiles фиксирует координатор.
- Обработка данных: отдельная CLI-команда пакета city_data; длительный импорт не запускается внутри пользовательского HTTP-запроса.
- Redis, Kubernetes, очередь сообщений и самостоятельный vector database не являются зависимостями первой интеграции. Их добавляют только после измеренной потребности.

Это модульный монолит: пакеты разделяют ответственность, но не требуют отдельных сетевых сервисов и отдельных deployment для каждого агента.

Координатор владеет общими контрактами, миграциями, корневыми dependencies и lockfiles. Изменения в общих областях сначала оформляются как конкретное предложение, затем принимаются одним PR. Агент не меняет чужой пакет для обхода несогласованного интерфейса.

## 3. Единый контракт и порядок его изменения

contracts.schema.json в корне остаётся каноническим источником. scripts/generate_contracts.py генерирует installable bundled copies в packages/contracts и TypeScript в packages/api_client; --check исключает рассинхронизацию. Ручное редактирование сгенерированных копий запрещено.

Из canonical schemas должны генерироваться TypeScript-типы, Python-модели или их проверяемые эквиваленты, а также request/response fixtures. OpenAPI описывает HTTP-пути и ссылается на те же модели. Ручные копии DTO в разных пакетах недопустимы.

Пока поле или внутренний интерфейс отсутствует в canonical schema, он считается предложением. Зависимый агент может реализовать изолированную логику за adapter и локальными тестами; интеграция блокируется до merge контракта. Имена из этого документа не дают разрешения создавать несовместимые альтернативные DTO.

Правила контракта:

- Версия HTTP API: /v1. Ошибки имеют стабильный code и request_id.
- Координаты в обычных DTO: объект с lat и lon; геометрия GeoJSON использует порядок longitude, latitude.
- Все API-бюджеты и длительности — секунды; расстояния — метры. UI может показывать минуты и километры.
- Деньги: целое число минимальных денежных единиц и явная валюта; для KZT точность задаётся контрактом, без неявного float.
- Даты — RFC 3339 с timezone. Городская timezone: Asia/Almaty. Нельзя зависеть от timezone сервера.
- Язык: ru, kk или en. Fallback названия места не означает наличие подтверждённого перевода.
- Отсутствие значения, false и неизвестное значение различаются.
- Ограничения имеют strength: required или preferred. Required нельзя незаметно превратить в preferred.
- Максимальное число основных рекомендаций — 3. У списка POI на карте отдельная пагинация.
- Новые необязательные поля добавляют совместимо; изменение смысла поля требует отдельного решения координатора.

## 4. HTTP API

| Метод и путь | Назначение |
|---|---|
| GET /v1/health/live | Процесс API отвечает |
| GET /v1/health/ready | БД и нужные для работы ресурсы готовы |
| GET /v1/places | POI для карты и поиска: bbox, query, категории, cursor |
| GET /v1/places/{id} | Карточка места, факты, источники, даты |
| POST /v1/recommendations | Отобрать 1–3 места и объяснить результат |
| POST /v1/itineraries | Рассчитать последовательность выбранных остановок |
| POST /v1/feedback | Добровольная оценка результата без обязательного сырого запроса |
| GET /v1/data-status | Публичное покрытие и свежесть базы |

Пути, которых ещё нет в зафиксированной схеме, реализуются после принятия соответствующего contract change. Runtime OpenAPI не должен расходиться с зафиксированными схемами.

Запрос рекомендаций включает текст, язык, точку начала, время начала, доступный бюджет в секундах, способ передвижения, признак возвращения в начальную точку и ограничения. Для диалогового уточнения клиент передаёт предыдущее нормализованное состояние и изменение условий по отдельному согласованному контракту: сервер не должен скрыто хранить бессрочную историю.

Ответ различает статусы matched, partial, no_match и needs_clarification. Он включает нормализованное намерение, рекомендации, неизвестные или невыполненные условия, источники, контекст, предупреждения и список недоступных зависимостей. Partial не разрешает представить место с нарушенным required-условием как подходящее: возможные альтернативы показываются отдельно и требуют решения пользователя.

## 5. Основные сущности

| Сущность | Ключевые данные |
|---|---|
| Place | Стабильный ID, внешние идентификаторы, названия, координаты, категории, адрес |
| PlaceFact | Атрибут, значение, состояние known / unknown / conflicting, evidence IDs, дата проверки |
| Source | Тип, URL, лицензия, время получения, хеш содержимого |
| SourceDocument / Chunk | Исходный текст, язык, связь с местом, ссылка на source, embeddings |
| OpeningHours | Исходная строка, нормализованное расписание, timezone и известные исключения |
| IngestionRun | Источник, начало/окончание, числа объектов, ошибки и coverage |
| RouteEstimate | Профиль, расстояние, длительность, геометрия, provider, routed / approximate |
| VisitEstimate | Диапазон времени, основание source / heuristic / model, пояснение |

Состояние факта и его булево значение независимы. Например, wheelchair_accessible = false с источником означает подтверждённое отсутствие; unknown означает, что доказательств нет. Конфликтующие источники сохраняются и видны, а не перезаписываются последним импортом без пояснения.

Повторный импорт идемпотентен. Внешняя идентичность объекта и canonical place ID сохраняются. Deduplication не объединяет объекты только по совпадению названия. Для не найденного при обновлении места требуется отдельная политика устаревания; отсутствие в одном ответе провайдера не доказывает закрытие.

Embeddings хранят model ID, размерность и версию preprocessing. Индекс с другой размерностью нельзя использовать без миграции и переиндексации. На небольшом наборе допустим exact vector search; необходимость approximate index подтверждается замерами.

## 6. Публичные границы Python-пакетов

Foundation-изменение координатора фиксирует типы и сигнатуры этих портов в packages/contracts. До его принятия таблица описывает ответственность, а не разрешает агентам независимо объявить несовместимые классы.

| Порт | Вход | Выход | Исполнитель |
|---|---|---|---|
| PlaceRepository | Place IDs или структурированный поиск с географией | Places с фактами и provenance | city_data |
| Retriever | Нормализованный запрос, фильтры, locale, лимит кандидатов | Candidate IDs, component scores, evidence IDs, retrieval mode | retrieval |
| RouteProvider | Точки, transport profile, время запроса | RouteEstimate или явная provider error | city_context |
| ContextProvider | Origin, start time, timezone, кандидатные места | Погода, opening status, freshness, недоступные сервисы | city_context |
| Recommender | Canonical request и внедрённые зависимости | Canonical recommendation response | recommender |

services/api создаёт реальные адаптеры и внедряет их в orchestration. Пакеты не импортируют HTTP-приложение, не читают друг у друга private modules и не открывают внешние подключения при import. Секреты и конфигурация передаются явно через composition root.

retrieval отвечает за релевантность кандидатов, recommender — за выполнимость плана и итоговый ответ. LLM-провайдер находится за заменяемым adapter; название модели и credentials задаются конфигурацией, а не копируются в код нескольких пакетов.

## 7. Поток рекомендаций

1. Проверить размер запроса, координаты, единицы, дату и ограничения.
2. Получить структурированное намерение; явные пользовательские фильтры имеют приоритет над предположением модели.
3. Применить географический и factual prefilter к подтверждённым required-условиям.
4. Выполнить lexical и multilingual vector retrieval; объединить результаты и оценить релевантность.
5. Для ограниченного числа лучших кандидатов получить реальные маршруты, opening status и погоду.
6. Проверить временной бюджет: дорога, посещение, переходы, резерв и возвращение, если оно запрошено.
7. Выбрать разнообразные 1–3 варианта, объяснив компромиссы по preferred-условиям.
8. Передать генератору только найденные факты, расчёты и evidence IDs.
9. Проверить ответ по schema, допустимым place IDs и ссылкам на evidence; при сбое использовать детерминированное объяснение.

Часы работы и интервалы посещения проверяются на запланированное время, а не только на текущую минуту. Неполное расписание и неизвестные праздничные исключения могут давать unknown. Статус open нельзя выводить из отсутствия отметки closed.

Модель не вычисляет маршрут, не придумывает цены, удобства и часы работы. Предложение занятия маркируется как идея; оно не должно подразумевать неподтверждённое наличие услуги. Пользовательские и загруженные тексты считаются данными, а не инструкциями для изменения поведения системы.

## 8. Провайдеры и деградация

- POI: OSM / Overpass и отдельные разрешённые источники. Сохранять attribution, license и дату. Ограничивать объём запросов, кэшировать, уважать условия конкретного сервера.
- Погода: Open-Meteo adapter. Бесплатный hosted endpoint предназначен для некоммерческого использования и ограничен; для коммерческого deployment выбирается подходящий тариф или иной провайдер.
- Маршруты: openrouteservice или иной согласованный провайдер с нужным профилем. Основной профиль — walking. Car-only endpoint нельзя выдавать за пешую маршрутизацию.
- Геокодирование: выбор точки и поиск в собственной базе доступны без внешнего геокодера. Внешний сервис подключается отдельным adapter после проверки его условий.
- Карта: MapLibre — renderer. Tile provider, attribution, quotas и offline-права проверяются отдельно; renderer не предоставляет безлимитные бесплатные тайлы.

Сбой weather provider не должен ломать поиск. Недоступный route provider позволяет показать расстояние по прямой и явно приблизительную оценку; нельзя рисовать выдуманную дорожную геометрию или обещать соблюдение жёсткого временного бюджета. Недоступность embeddings включает lexical mode с явной отметкой. Недоступность LLM включает проверяемый шаблон ответа по найденным данным.

Fixture mode включается явно и маркируется в UI. Данные fixture нельзя представлять как актуальный импорт или живой ответ провайдера. Кэш показывает дату; просроченное значение не становится текущим от того, что внешний API недоступен.

## 9. Приватность и эксплуатация

- Геолокация запрашивается только после действия пользователя. Выбор точки вручную всегда доступен.
- Точные координаты используются в памяти для выполнения запроса и по умолчанию не сохраняются в логи, feedback или analytics.
- Генератору передаются места и рассчитанные характеристики; точные координаты пользователя ему не нужны.
- Погодный запрос по возможности использует округлённую географическую ячейку. Для маршрута внешнему провайдеру могут потребоваться точные точки; это объясняется пользователю в privacy notice.
- Фавориты и планы первоначально хранятся на устройстве. Добавление аккаунтов требует отдельного retention и deletion flow.
- API keys находятся только на сервере. Логи исключают authorization headers, ключи и содержимое чувствительных запросов.
- У всех сетевых операций есть timeout; retry ограничен и применяется только когда операция допускает повтор. Ограничены размер запросов, число кандидатов и частота обращений.
- Импорт не должен загружать произвольный URL из пользовательского текста: источники и URL проверяются, private/internal network targets запрещаются.

## 10. Проверка и интеграция

CI проверяет canonical schemas и fixtures, Python lint/type checks и релевантные pytest, frontend lint/type checks/build, package boundaries и smoke тесты с fixtures. Проверки live providers выполняются отдельно от детерминированного CI и явно отмечают пропуск при отсутствии credentials.

Интеграция идёт слоями: contracts и fixtures → работающий импорт и API places → frontend с реальными POI → retrieval → recommender и контекст → планы и уточнения → evaluation и UX QA → deployment и защита. Не ждать готовности всех необязательных функций, чтобы впервые проверить совместимость пакетов.

Каждый PR содержит цель, затронутые contracts, выполненные проверки, необходимые env variables и известные ограничения. Секреты, большие raw datasets и локальные embeddings в git не коммитятся. Synthetic fixtures обозначаются явно. Изменение схемы БД поступает координатору как предложение миграции; одно изменение не должно порождать несколько конфликтующих migration heads.
